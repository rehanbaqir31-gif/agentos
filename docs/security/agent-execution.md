# Agent execution security

Agent prompts, repository content, tool output, and model output are untrusted. Run adapters only inside an AgentOS-managed isolated runtime with a run-scoped workspace, explicit resource and network policy, no host credentials, and no Docker socket. A separate Git worktree protects developer edits from direct mutation but is not a security boundary. Never silently execute on the host if a sandbox is missing.

OpenCode permissions are an additional application-level control, not an OS sandbox. `ExecutionCoordinator` currently permits only `read_only`; permission requests are persisted as rejected before sending the rejection response, and secret-like strings are redacted from grant descriptions/resources. `ApprovalAuthorizationService.grantPermission()` creates a permission grant for the authenticated principal after server policy authorizes it. This is a self-grant under policy, not a separate human approval. Principal/run/action/policy/expiry binding is enforced, and grant consumption plus its audit event are atomic in SQLite and PostgreSQL. A policy adapter returns one immutable `(authorized, version)` decision snapshot; a policy deployment after that snapshot is evaluated does not invalidate that in-flight decision. Cancellation observed at an in-transaction checkpoint before commit rolls back consumption and its event. A cancellation arriving after the last checkpoint may race the database commit; if commit wins, the grant and audit remain persisted and the grant stays consumed. The service accepts no client principal argument and fails closed if trusted identity or policy is absent. No concrete authenticated identity source exists; therefore the service is infrastructure only and is not wired to enable supervised execution. The Docker runtime mounts one detached worktree read-only, creates a per-run bridge with masquerading and inter-container communication disabled, publishes the authenticated server only on host loopback, runs as UID/GID 10001, uses a read-only root filesystem, drops all capabilities, sets no-new-privileges, applies PID/memory/CPU limits, and bounds `/tmp` with a 256 MiB tmpfs. Only `HOME=/tmp` and the random server password are explicitly passed into the container; no Docker socket is mounted. The image must be supplied by deployment configuration and pinned by digest. The Docker CLI child receives a filtered environment rather than the whole host environment. The bridge can still reach host-gateway services; host firewall rules must restrict sensitive listeners.

Runtime command construction remains covered by unit doubles. GitHub Actions run [42378655753](https://github.com/rehanbaqir31-gif/agentos/actions/runs/42378655753) passed the separate real-daemon suite on Docker Engine 29.4.2 / API 1.54 (Ubuntu 26.04.1 x64). It uses a disposable Node-based OpenCode protocol shim to inspect effective settings, deny workspace and host-canary reads, probe external egress, stop a real process, and check generation cleanup. The local Windows environment has no Docker executable. The shim does not verify OpenCode or model execution. A digest pins image bytes; it does not establish that the image is trustworthy. The non-masquerading Docker bridge blocks ordinary external routing but can reach host-gateway services; enforce host firewall restrictions. Remote model access remains unavailable under this network policy; local model/provider configuration must be provisioned inside a trusted image or a future credential/network broker must be implemented. Supervised/autonomous execution remains disabled until trusted server identity is connected to policy and approvals are enforced immediately before execution. Durable result artifacts are captured as described below; OpenCode process output and tests remain unavailable. Docker is not a complete boundary against a malicious host kernel or daemon.

## Result artifact handling

Result binaries are stored outside database event payloads under an AgentOS-owned local object root (default `~/.agentos/artifacts`). Metadata is scoped by the composite run/project relationship and artifact ID; callers must provide all three IDs to read. Locators are opaque relative UUID keys and do not reveal host paths. Staged files use restrictive permissions, are flushed and digest-checked before atomic no-overwrite promotion, and are verified again when read. The service refuses traversal locators and symlinked object directories, limits captures to 5 MiB per artifact and 25 MiB per run by default, records truncation, and supports retention cleanup. Keep the configured root writable only by the AgentOS service account and protect it with the host's backup/access-control policy.

Text outputs pass through the existing secret redactor. Structured artifacts reject secret-bearing field names; execution manifests contain environment variable names only. The OpenCode adapter currently does not expose process stdout/stderr or structured test results, so those rows are marked unavailable. AgentOS does not collect model chain-of-thought. Filesystem storage is the only implemented backend; no cloud credentials are accepted. Filesystem tests cover promotion failure, truncation, invalid locators and database-backed retrieval/integrity; Windows prevents the symlink-specific adversarial tests from running here. Real Docker and OpenCode remain unverified.

The OpenCode SDK response includes assistant text parts. AgentOS persists only non-synthetic, non-ignored `text` parts as the run summary after redaction; reasoning parts are excluded. This does not provide process stdout/stderr or structured test output, which remain unavailable artifacts. The protocol-shim daemon suite is not live OpenCode verification. The official 1.19.5 image and digest candidate are recorded in [the OpenCode integration notes](../integrations/opencode.md), but its startup/task behavior has not been exercised by AgentOS.

The current runtime passes only `HOME` and the generated server password into the container and supplies no provider credential/configuration. Its bridge blocks ordinary external egress. With no local provider path and no Docker daemon on the current Windows machine, a model-backed smoke test and real-image cancellation/failure checks are blocked. Do not weaken this profile or claim a live task to work around the missing test setup.

## Worker ownership and recovery

Each run has a durable worker lease with a monotonically increasing generation. Claim, renewal and release check the generation as well as worker ID; stale workers cannot release a newer lease. The coordinator heartbeats leases and aborts when renewal fails. Recovery claims only an expired or released lease, labels cleanup by the prior generation, preserves artifacts, records a recovery event and marks the run interrupted without replaying its prompt. Runtime containers and internal networks carry run and generation labels; daemon cleanup filters the exact generation. Lease table creation is atomic with run creation. SQLite and PGlite checks pass locally; real PostgreSQL 16 row-lock behavior is verified only by CI. Local Docker daemon verification is blocked because Docker is unavailable; a daemon integration job has been added to CI. A lease timeout is a failure detector with bounded timing assumptions, not proof that a prior process has stopped; callers must fail closed when a lease write is rejected. `read_only` remains the only enabled execution mode.
